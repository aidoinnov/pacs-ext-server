# GC Batch Job - 배포 및 운영 가이드

> **작성일**: 2026-01-12  
> **목적**: GC 배치 작업 배포 및 운영 절차

---

## 📋 배포 개요

### 배포 전략
1. **Dry-run 모드로 1주일 검증** - 프로덕션 데이터로 안전성 확인
2. **점진적 활성화** - PENDING 타임아웃 → FAILED 정리 → Orphan 정리
3. **모니터링 강화** - 로그 및 메트릭 수집

## 1️⃣ 바이너리 빌드

> **참고**: 상세한 바이너리 구조는 [06-아키텍처-및-바이너리-구조.md](./06-아키텍처-및-바이너리-구조.md) 참조

### Cargo.toml 설정

```toml
# pacs-server/Cargo.toml

[lib]
name = "pacs_server"
path = "src/lib.rs"

# API 서버 바이너리
[[bin]]
name = "pacs-server"
path = "src/bin/server.rs"
required-features = ["server"]

# GC 배치 바이너리
[[bin]]
name = "gc_runner"
path = "src/bin/gc_runner.rs"
required-features = ["gc"]

[features]
default = ["server"]
server = ["axum", "tower", "tower-http"]
gc = ["clap"]
```

### 빌드 명령

```bash
# GC 배치 바이너리만 빌드
cargo build --bin gc_runner --features gc

# 릴리스 빌드
cargo build --release --bin gc_runner --features gc

# 실행 테스트
./target/release/gc_runner --help
./target/release/gc_runner --job=snapshot --dry-run=true

# 전체 빌드 (API 서버 + GC 배치)
cargo build --release
```

## 3️⃣ Kubernetes CronJob 배포

### CronJob YAML

```yaml
# k8s/cronjobs/gc-snapshot-job.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: gc-snapshot-job
  namespace: pacs-production
  labels:
    app: pacs-server
    component: gc-batch
spec:
  # 매일 새벽 3시 실행 (KST 기준)
  schedule: "0 18 * * *"  # UTC 18:00 = KST 03:00
  
  # 동시 실행 방지
  concurrencyPolicy: Forbid
  
  # 성공한 Job 3개, 실패한 Job 1개 보관
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  
  # Job 타임아웃 (2시간)
  jobTemplate:
    spec:
      activeDeadlineSeconds: 7200
      backoffLimit: 0  # 재시도 없음
      
      template:
        metadata:
          labels:
            app: pacs-server
            component: gc-batch
        spec:
          restartPolicy: Never
          
          containers:
          - name: gc-runner
            image: your-registry/pacs-server:latest
            # ⭐ gc_runner 바이너리 실행
            command: ["/app/gc_runner"]
            args:
              - "--job=snapshot"
              - "--dry-run=true"  # ⚠️ 1주일 후 false로 변경

            env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: pacs-db-secret
                  key: database-url
            
            - name: AWS_REGION
              value: "ap-northeast-2"
            
            - name: S3_BUCKET_NAME
              value: "pacs-production-storage"
            
            - name: GC_DRY_RUN
              value: "true"  # ⚠️ 1주일 후 false로 변경
            
            - name: GC_BATCH_SIZE
              value: "1000"
            
            - name: GC_PENDING_GRACE_DAYS
              value: "3"
            
            - name: GC_FAILED_GRACE_DAYS
              value: "7"

            - name: RUST_LOG
              value: "info,gc_runner=debug"

            resources:
              requests:
                memory: "256Mi"
                cpu: "100m"
              limits:
                memory: "512Mi"
                cpu: "500m"
            
            # AWS 자격 증명 (IRSA 사용)
            serviceAccountName: pacs-gc-service-account
```

### 배포 명령

```bash
# 1. Dry-run 모드로 배포
kubectl apply -f k8s/cronjobs/gc-snapshot-job.yaml

# 2. 즉시 실행 테스트
kubectl create job --from=cronjob/gc-snapshot-job gc-snapshot-manual-test -n pacs-production

# 3. 로그 확인
kubectl logs -f job/gc-snapshot-manual-test -n pacs-production

# 4. Job 삭제
kubectl delete job gc-snapshot-manual-test -n pacs-production
```

## 4️⃣ Dry-run 검증 (1주일)

### 검증 항목

#### 1. 로그 확인

```sql
-- 배치 실행 횟수
SELECT 
    DATE(created_at) as date,
    COUNT(DISTINCT batch_id) as batch_count,
    COUNT(*) as total_logs
FROM gc_deletion_log
WHERE created_at > NOW() - INTERVAL '7 days'
GROUP BY DATE(created_at)
ORDER BY date DESC;

-- Dry-run 결과 요약
SELECT 
    reason,
    COUNT(*) as count,
    COUNT(DISTINCT annotation_id) as unique_annotations
FROM gc_deletion_log
WHERE dry_run = true
  AND created_at > NOW() - INTERVAL '7 days'
GROUP BY reason
ORDER BY count DESC;

-- 삭제 예정 Snapshot 목록
SELECT 
    annotation_id,
    s3_key,
    reason,
    created_at
FROM gc_deletion_log
WHERE dry_run = true
  AND created_at > NOW() - INTERVAL '1 day'
ORDER BY created_at DESC
LIMIT 100;
```

#### 2. 예상 삭제량 확인

```sql
-- PENDING 타임아웃 대상
SELECT COUNT(*) as pending_count
FROM annotations
WHERE snapshot_upload_status = 'pending'
  AND updated_at < NOW() - INTERVAL '3 days';

-- FAILED 삭제 대상
SELECT COUNT(*) as failed_count
FROM annotations
WHERE snapshot_upload_status = 'failed'
  AND snapshot_image_key IS NOT NULL
  AND updated_at < NOW() - INTERVAL '7 days';
```

#### 3. 오탐 검증

```sql
-- 최근 업로드된 Snapshot이 삭제 대상인지 확인 (오탐)
SELECT 
    a.id,
    a.snapshot_upload_status,
    a.snapshot_uploaded_at,
    a.updated_at,
    g.reason,
    g.created_at as gc_log_created_at
FROM annotations a
JOIN gc_deletion_log g ON a.id = g.annotation_id
WHERE a.snapshot_uploaded_at > NOW() - INTERVAL '1 day'
  AND g.dry_run = true
  AND g.created_at > NOW() - INTERVAL '1 day';

-- 결과가 0이어야 정상
```

### 검증 통과 기준

- ✅ 7일 동안 오류 없이 실행
- ✅ 오탐 0건 (최근 업로드된 Snapshot이 삭제 대상이 아님)
- ✅ 예상 삭제량이 합리적 (전체 Snapshot의 5% 미만)
- ✅ 로그가 정상적으로 기록됨

### 첫 실행 후 검증

```sql
-- 실제 삭제 결과 확인
SELECT 
    reason,
    status,
    COUNT(*) as count,
    SUM(file_size) as total_size_bytes
FROM gc_deletion_log
WHERE dry_run = false
  AND created_at > NOW() - INTERVAL '1 hour'
GROUP BY reason, status
ORDER BY count DESC;

-- 실패 건수 확인
SELECT 
    annotation_id,
    s3_key,
    error_code,
    error_message
FROM gc_deletion_log
WHERE dry_run = false
  AND status = 'failed'
  AND created_at > NOW() - INTERVAL '1 hour';
```

## 6️⃣ 모니터링

### 로그 쿼리 (운영용)

```sql
-- 일별 삭제 통계
SELECT 
    DATE(created_at) as date,
    reason,
    COUNT(*) as count,
    SUM(file_size) / 1024 / 1024 as total_mb
FROM gc_deletion_log
WHERE dry_run = false
  AND created_at > NOW() - INTERVAL '30 days'
GROUP BY DATE(created_at), reason
ORDER BY date DESC, count DESC;

-- 실패율 모니터링
SELECT 
    DATE(created_at) as date,
    COUNT(*) FILTER (WHERE status = 'success') as success_count,
    COUNT(*) FILTER (WHERE status = 'failed') as failed_count,
    ROUND(100.0 * COUNT(*) FILTER (WHERE status = 'failed') / COUNT(*), 2) as failure_rate
FROM gc_deletion_log
WHERE dry_run = false
  AND created_at > NOW() - INTERVAL '7 days'
GROUP BY DATE(created_at)
ORDER BY date DESC;
```

### 알림 설정 (선택)

```yaml
# Prometheus AlertManager 규칙
groups:
- name: gc_batch_alerts
  rules:
  - alert: GcBatchHighFailureRate
    expr: |
      (
        sum(rate(gc_deletion_failed_total[1h])) 
        / 
        sum(rate(gc_deletion_total[1h]))
      ) > 0.1
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "GC Batch 실패율 10% 초과"
      description: "지난 1시간 동안 GC Batch 실패율이 {{ $value }}%입니다."
  
  - alert: GcBatchNotRunning
    expr: |
      time() - gc_batch_last_run_timestamp > 86400 * 2
    for: 1h
    labels:
      severity: critical
    annotations:
      summary: "GC Batch가 2일 이상 실행되지 않음"
      description: "마지막 실행: {{ $value }}초 전"
```

## 7️⃣ 트러블슈팅

### 문제 1: Job이 실행되지 않음

**증상**:
```bash
kubectl get cronjobs -n pacs-production
# LAST SCHEDULE: <none>
```

**원인**:
- CronJob 스케줄 문법 오류
- ServiceAccount 권한 부족

**해결**:
```bash
# 스케줄 검증
kubectl describe cronjob gc-snapshot-job -n pacs-production

# 수동 실행 테스트
kubectl create job --from=cronjob/gc-snapshot-job test-job -n pacs-production
```

### 문제 2: S3 삭제 실패

**증상**:
```sql
SELECT * FROM gc_deletion_log 
WHERE status = 'failed' 
  AND error_message LIKE '%S3%';
```

**원인**:
- IAM 권한 부족
- S3 버킷 정책 제한
- 네트워크 타임아웃

**해결**:
```bash
# IAM 권한 확인
aws iam get-role-policy --role-name pacs-gc-role --policy-name s3-delete-policy

# S3 버킷 정책 확인
aws s3api get-bucket-policy --bucket pacs-production-storage
```

### 문제 3: DB 연결 실패

**증상**:
```
Error: Failed to connect to database
```

**원인**:
- DATABASE_URL 환경 변수 누락
- DB 연결 풀 고갈
- 네트워크 정책 제한

**해결**:
```bash
# Secret 확인
kubectl get secret pacs-db-secret -n pacs-production -o yaml

# Pod 환경 변수 확인
kubectl exec -it <pod-name> -n pacs-production -- env | grep DATABASE
```
