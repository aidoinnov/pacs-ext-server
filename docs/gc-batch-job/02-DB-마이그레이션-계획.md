## 1️⃣ GC 로그 테이블 (039_create_gc_deletion_log.sql)

### 목적
- GC 배치 작업의 삭제 로그 기록
- 운영 및 디버깅용 (감사 로그와 분리)
- Dry-run 모드 검증 지원

### 스키마

```sql
-- 039_create_gc_deletion_log.sql
CREATE TABLE gc_deletion_log (
    id BIGSERIAL PRIMARY KEY,
    batch_id VARCHAR(100) NOT NULL,          -- 배치 실행 ID (UUID)
    resource_type VARCHAR(50) NOT NULL,      -- 'snapshot' or 'mask'
    s3_key VARCHAR(512) NOT NULL,
    
    -- 리소스 식별
    annotation_id BIGINT NULL,
    mask_id BIGINT NULL,
    mask_group_id BIGINT NULL,
    version INTEGER NULL,
    
    -- 삭제 이유 및 결과
    reason VARCHAR(100) NOT NULL,            -- 'orphan', 'stale', 'failed', 'pending_timeout', 'annotation_deleted'
    dry_run BOOLEAN NOT NULL DEFAULT true,
    status VARCHAR(50) NOT NULL,             -- 'success', 'failed', 'skipped'
    error_code VARCHAR(100) NULL,
    error_message TEXT NULL,
    
    -- 메타데이터
    grace_period_days INTEGER NULL,          -- 적용된 유예 기간
    file_size BIGINT NULL,                   -- 삭제된 파일 크기 (통계용)
    
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 인덱스
CREATE INDEX idx_gc_log_batch_id ON gc_deletion_log(batch_id);
CREATE INDEX idx_gc_log_created_at ON gc_deletion_log(created_at);
CREATE INDEX idx_gc_log_resource_type ON gc_deletion_log(resource_type);
CREATE INDEX idx_gc_log_reason ON gc_deletion_log(reason);
CREATE INDEX idx_gc_log_annotation_id ON gc_deletion_log(annotation_id) WHERE annotation_id IS NOT NULL;

-- 코멘트
COMMENT ON TABLE gc_deletion_log IS 'GC 배치 작업의 삭제 로그 (운영/디버깅용)';
COMMENT ON COLUMN gc_deletion_log.batch_id IS '배치 실행 ID (같은 실행의 로그를 그룹화)';
COMMENT ON COLUMN gc_deletion_log.reason IS '삭제 이유: orphan(DB 없음), stale(구버전), failed(실패 상태), pending_timeout(타임아웃), annotation_deleted(어노테이션 삭제)';
COMMENT ON COLUMN gc_deletion_log.dry_run IS 'Dry-run 모드 여부 (true: 실제 삭제 안 함)';
COMMENT ON COLUMN gc_deletion_log.status IS '삭제 결과: success(성공), failed(실패), skipped(건너뜀)';
```

### 로그 보존 정책 (선택)

```sql
-- 1년 이상 된 로그 자동 삭제 (CronJob으로 실행)
DELETE FROM gc_deletion_log
WHERE created_at < NOW() - INTERVAL '1 year';
```

## 2️⃣ Mask 상태 관리 추가 (038_add_mask_upload_status.sql)

### 목적
- Mask 업로드 상태 추적
- PENDING 타임아웃 및 FAILED Mask 정리 지원
- Snapshot과 동일한 상태 관리 체계 구축

### 스키마

```sql
-- 038_add_mask_upload_status.sql

-- 1. ENUM 타입 생성
CREATE TYPE mask_upload_status AS ENUM (
    'pending',
    'uploading',
    'completed',
    'failed'
);

-- 2. 컬럼 추가
ALTER TABLE annotation_mask
ADD COLUMN upload_status mask_upload_status NULL DEFAULT 'completed',  -- 기존 데이터는 completed로
ADD COLUMN uploaded_at TIMESTAMPTZ NULL DEFAULT CURRENT_TIMESTAMP;     -- 기존 데이터는 created_at 복사

-- 3. 기존 데이터 마이그레이션
UPDATE annotation_mask
SET uploaded_at = created_at
WHERE uploaded_at IS NULL;

-- 4. 인덱스 생성
CREATE INDEX idx_mask_upload_status 
ON annotation_mask(upload_status)
WHERE upload_status IS NOT NULL;

CREATE INDEX idx_mask_uploaded_at
ON annotation_mask(uploaded_at)
WHERE uploaded_at IS NOT NULL;

-- 5. 코멘트
COMMENT ON COLUMN annotation_mask.upload_status IS 'Mask 업로드 상태: pending(대기), uploading(업로드 중), completed(완료), failed(실패)';
COMMENT ON COLUMN annotation_mask.uploaded_at IS 'Mask 업로드 완료 시간 (성공 시만 기록)';
```

### 마이그레이션 전략

#### 기존 데이터 처리
```sql
-- 모든 기존 Mask는 'completed' 상태로 간주
-- (이미 업로드된 데이터이므로)
ALTER TABLE annotation_mask
ADD COLUMN upload_status mask_upload_status NULL DEFAULT 'completed';

-- uploaded_at은 created_at으로 초기화
UPDATE annotation_mask
SET uploaded_at = created_at
WHERE uploaded_at IS NULL;
```

#### 롤백 계획
```sql
-- 038_add_mask_upload_status.sql 롤백
ALTER TABLE annotation_mask
DROP COLUMN IF EXISTS upload_status,
DROP COLUMN IF EXISTS uploaded_at;

DROP TYPE IF EXISTS mask_upload_status;
```

## 5️⃣ 리스크 및 대응

### GC 로그 테이블

**리스크**: 낮음
- 새 테이블 추가만 하므로 기존 시스템에 영향 없음

**대응**:
- 스테이징에서 1일 검증 후 프로덕션 배포

### Mask 상태 관리

**리스크**: 중간
- 기존 테이블 수정 (컬럼 추가)
- 기존 데이터 마이그레이션 필요

**대응**:
- 개발 환경에서 충분한 테스트
- 스테이징에서 1주일 검증
- 롤백 계획 준비
- 프로덕션 배포 시 점검 시간 확보
