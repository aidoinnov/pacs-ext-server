## 1️⃣ Snapshot 상태 관리 (✅ 완벽)

### DB 스키마

```sql
-- annotations 테이블
CREATE TYPE snapshot_upload_status AS ENUM (
    'pending',
    'uploading',
    'completed',
    'failed'
);

ALTER TABLE annotations
ADD COLUMN snapshot_upload_status snapshot_upload_status NULL,
ADD COLUMN snapshot_uploaded_at TIMESTAMPTZ NULL,
ADD COLUMN snapshot_image_key VARCHAR(512) NULL;

-- 인덱스
CREATE INDEX idx_annotations_snapshot_upload_status 
ON annotations(snapshot_upload_status)
WHERE snapshot_upload_status IS NOT NULL;

CREATE INDEX idx_annotations_snapshot_uploaded_at
ON annotations(snapshot_uploaded_at)
WHERE snapshot_uploaded_at IS NOT NULL;
```

### 상태 전이 다이어그램

```
NULL → pending (URL 생성) → completed (업로드 성공)
                          → failed (업로드 실패)
```

**참고**: `uploading` 상태는 ENUM에 정의되어 있지만 실제로 사용되지 않음 (클라이언트 직접 업로드 방식)

### ✅ GC 준비 상태

**즉시 구현 가능한 작업**:
1. ✅ **PENDING 타임아웃** - 3일 이상 pending → failed 전환
2. ✅ **FAILED 정리** - 7일 이상 failed → S3 삭제
3. ✅ **Orphan 정리** - DB에 없는 S3 오브젝트 삭제 (S3 스캔 필요)

## 2️⃣ Mask 상태 관리 (⏳ 마이그레이션 필요)

### 현재 DB 스키마

```sql
-- annotation_mask 테이블
CREATE TABLE annotation_mask (
    id BIGSERIAL PRIMARY KEY,
    annotation_id BIGINT NOT NULL,
    mask_group_id BIGINT NOT NULL,
    version INTEGER NOT NULL DEFAULT 1,
    image_key VARCHAR(512) NOT NULL,  -- ✅ S3 경로 존재
    uploaded_at TIMESTAMPTZ NULL,     -- ✅ 업로드 시간 존재
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### ❌ 누락된 부분

- **상태 ENUM 없음** - `upload_status` 필드 부재
- **상태 전이 로직 없음** - API에서 상태 관리 안 함
- **실패 처리 없음** - 업로드 실패 시 처리 로직 부재

### ⚠️ GC 제약 사항

**현재 가능한 작업**:
- ✅ `uploaded_at` 기반 오래된 Mask 정리 (단, 어노테이션 삭제 시만)
- ✅ Orphan Mask 정리 (DB에 없는 S3 오브젝트)

**불가능한 작업**:
- ❌ PENDING 타임아웃 (상태 필드 없음)
- ❌ FAILED Mask 정리 (상태 필드 없음)

## 3️⃣ 권장 개발 순서

### Phase 1: Snapshot GC (2주) - ✅ 즉시 시작 가능

**필요한 작업**:
1. GC 로그 테이블 생성 (`gc_deletion_log`)
2. Snapshot GC 로직 구현
3. Dry-run 모드로 1주일 검증

**장점**:
- DB 마이그레이션 불필요
- 기존 필드만으로 모든 기능 구현 가능
- 빠른 검증 및 피드백

### Phase 2: Mask 상태 관리 추가 (2주)

**필요한 작업**:
1. DB 마이그레이션 (`mask_upload_status` 추가)
2. API 수정 (URL 생성/완료 처리)
3. 기존 데이터 마이그레이션

**장점**:
- Snapshot GC 경험 활용
- 안정적인 마이그레이션 가능

### Phase 3: Mask GC 구현 (1주)

**필요한 작업**:
1. Mask GC 로직 추가
2. 통합 테스트
3. 프로덕션 배포

## 📊 결론

### ✅ 즉시 시작 가능
- **Snapshot GC** - 모든 필드와 로직이 완벽하게 준비됨
- **GC 로그 테이블** - 별도 테이블로 분리하여 감사 로그와 독립적으로 관리

### ⏳ 추가 작업 필요
- **Mask 상태 관리** - DB 마이그레이션 및 API 수정 필요
- **Mask GC** - 상태 관리 구현 후 진행

### 🎯 권장 사항
1. **먼저 Snapshot GC 완성** - 검증된 설계로 빠른 구현
2. **Dry-run으로 1주일 검증** - 프로덕션 데이터로 안전성 확인
3. **Mask 상태 관리 추가** - Snapshot GC 경험 활용
4. **점진적 배포** - 리스크 최소화
