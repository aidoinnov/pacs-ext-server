## 1. 문서 목적

본 문서는 **DICOM Viewer에서 생성되는 어노테이션 캡쳐 이미지의 저장 방식**에 대해

여러 대안을 비교·검토하고, **최종적으로 채택한 저장 아키텍처와 그 근거를 명확히 기록**하기 위함이다.

해당 결정은 향후 다음 영역에 영향을 미친다.

- PACS 보조 서버 구조
- Annotation 데이터 모델
- Viewer ↔ Server 인터페이스
- 장기 저장, 성능, 확장성, 운영 전략

---

## 2. 배경 및 요구사항

### 2.1 배경

- TI DICOM Viewer에서 사용자가 어노테이션(측정, 마킹 등)을 수행
- 해당 어노테이션이 적용된 **최종 화면 상태를 이미지로 캡쳐**
- 어노테이션 정보 업데이트 시, 해당 이미지도 함께 저장 필요

### 2.2 주요 요구사항

| 항목 | 요구 |
| --- | --- |
| 저장 대상 | DICOM + Annotation이 합성된 캡쳐 이미지 |
| 데이터 특성 | 바이너리 이미지 (수십 KB ~ 수 MB) |
| 접근 방식 | Viewer / API / 향후 외부 연계 |
| 보안 | 인증된 사용자만 접근 |
| 확장성 | 장기적으로 이미지 수 증가 |
| 운영 | 백업, 복구, 성능 저하 방지 |

---

## 3. 검토 대상 아키텍처

### 3.1 대안 1 — DB에 이미지 직접 저장 (BLOB)

**설명**

- Annotation Update API에서 multipart/form-data로 이미지 파일 수신
- DB 컬럼(BLOB)에 이미지 데이터 직접 저장

**특징**

- 단일 트랜잭션 처리 가능
- 구현 초기에는 단순해 보임

---

### 3.2 대안 2 — 외부 저장소(S3 등)에 이미지 저장 + DB에 경로 저장

**설명**

- 서버에서 Signed URL 발급
- Viewer가 직접 외부 저장소(S3)에 이미지 업로드
- Annotation Update API에는 이미지 경로(object key)만 저장

## 4. 대안 비교 분석

| 비교 항목 | DB 직접 저장 | 외부 저장소(S3) |
| --- | --- | --- |
| 성능 | ❌ DB I/O 부담 증가 | ✅ 이미지 I/O 분리 |
| 확장성 | ❌ DB 용량 급증 | ✅ 스토리지 확장 용이 |
| 백업/복구 | ❌ 복잡 | ✅ 스토리지 정책 활용 |
| CDN 연계 | ❌ 불가 | ✅ 가능 |
| 업계 관행(PACS) | ❌ 비표준 | ✅ 일반적 |
| 운영 안정성 | ❌ 리스크 큼 | ✅ 검증된 패턴 |
| 보안 제어 | ⭕ | ⭕ (Signed URL) |

---

## 5. 최종 결정 사항

### ✅ **어노테이션 캡쳐 이미지는 외부 저장소(S3)에 저장하고, DB에는 경로만 저장한다**

---

## 6. 결정 근거

1. **PACS / 의료 영상 시스템 업계 표준 아키텍처**
    - 대용량 바이너리는 DB에 저장하지 않음
    - DB는 메타데이터 중심으로 유지
2. **성능 및 확장성**
    - Annotation 증가에 따른 DB 성능 저하 방지
    - 이미지 수 증가에 유연하게 대응 가능
3. **운영 및 유지보수**
    - DB 백업/마이그레이션 부담 최소화
    - 스토리지 정책 기반 수명 관리 가능
4. **보안 및 접근 제어**
    - Signed URL 기반 일회성 업로드
    - 서버는 파일 내용을 직접 취급하지 않음
5. **향후 확장 고려**
    - CDN 연계
    - 외부 시스템 연동
    - 이미지 재사용/재처리 가능

## 7. 채택된 아키텍처 개요

### 7.1 데이터 흐름 요약

```
[Viewer]
 ├─ DICOM + Annotation 화면 캡쳐
 ├─ 이미지 Blob 생성
 ├─ Signed URL 요청
 ├─ S3 업로드
 └─ Annotation Update (imageKey 포함)

[Server]
 ├─ 업로드 URL 발급
 └─ Annotation + imageKey 저장

[Storage]
 └─ 캡쳐 이미지 저장

```

---

## 8. 데이터 모델 반영 사항

### 8.1 Annotation 테이블 변경

```
snapshot_image_key (nullable)

```

- 외부 저장소 object key 저장
- 이미지가 없는 annotation도 허용

---

## 9. API 설계 방향 (요약)

- **이미지 업로드 API**
    - 파일 직접 수신 ❌
    - Signed URL 발급 ⭕
- **Annotation Update API**
    - 이미지 데이터 ❌
    - 이미지 경로(object key) ⭕

---

## 10. 고려하였으나 채택하지 않은 사항

### DB 직접 저장 방식 미채택 사유

- DB 성능 및 용량 리스크
- 장기 운영 시 기술 부채 가능성
- 의료 영상 시스템 특성과 부적합

---

## 11. 향후 고려 사항

- 이미지 업로드 실패 시 롤백 전략
- 이미지 포맷(WebP/PNG) 표준화
- 감사 로그 및 접근 추적
