# 기술문서: Annotation 응답에 사용자 이름 추가

## 📚 기술 개요

이 문서는 Annotation API 응답에 사용자 이름을 추가하면서 N+1 쿼리 문제를 해결한 배치 쿼리 최적화 기법을 설명합니다.

## 🎯 핵심 기술

### 1. N+1 쿼리 문제와 해결

#### 1.1 N+1 쿼리 문제란?

**정의**: 
- 메인 쿼리 1번 + 각 결과마다 추가 쿼리 N번 = 총 N+1번의 쿼리 실행
- ORM이나 관계형 데이터를 다룰 때 흔히 발생하는 성능 문제

**예시**:
```rust
// ❌ N+1 쿼리 발생 코드
let annotations = get_annotations().await?; // 1번 쿼리

for annotation in annotations {
    let user = get_user(annotation.user_id).await?; // N번 쿼리
    println!("{}: {}", user.name, annotation.data);
}
// 총 N+1번의 쿼리 실행!
```

**문제점**:
- 데이터베이스 왕복 횟수 증가
- 네트워크 오버헤드
- 응답 시간 증가
- DB 커넥션 풀 고갈 위험

#### 1.2 배치 쿼리 해결법

**핵심 아이디어**:
- 필요한 모든 ID를 먼저 수집
- 한 번의 쿼리로 모든 데이터 조회
- 메모리에서 매핑

**구현**:
```rust
// ✅ 배치 쿼리 최적화
let annotations = get_annotations().await?; // 1번 쿼리

// 1. 모든 user_id 수집
let user_ids: Vec<i32> = annotations
    .iter()
    .map(|a| a.user_id)
    .collect::<HashSet<_>>()  // 중복 제거
    .into_iter()
    .collect();

// 2. 한 번에 조회
let users = get_users_by_ids(&user_ids).await?; // 1번 쿼리

// 3. HashMap으로 빠른 매핑
let user_map: HashMap<i32, User> = users
    .into_iter()
    .map(|u| (u.id, u))
    .collect();

// 4. O(1) 조회
for annotation in annotations {
    if let Some(user) = user_map.get(&annotation.user_id) {
        println!("{}: {}", user.name, annotation.data);
    }
}
// 총 2번의 쿼리만 실행!
```

### 2. PostgreSQL ANY 연산자

#### 2.1 기본 사용법

**문법**:
```sql
SELECT * FROM table WHERE column = ANY(array_expression)
```

**예시**:
```sql
-- 여러 ID를 한 번에 조회
SELECT * FROM security_user 
WHERE id = ANY(ARRAY[1, 2, 3, 4, 5]);

-- 파라미터 바인딩
SELECT * FROM security_user 
WHERE id = ANY($1);  -- $1은 배열 타입
```

#### 2.2 SQLx에서 사용

```rust
async fn find_by_ids(&self, ids: &[i32]) -> Result<Vec<User>, sqlx::Error> {
    sqlx::query_as::<_, User>(
        "SELECT * FROM security_user WHERE id = ANY($1)"
    )
    .bind(ids)  // &[i32]를 직접 바인딩
    .fetch_all(&self.pool)
    .await
}
```

**장점**:
- IN 절보다 성능 우수 (특히 대량 데이터)
- 배열 타입 직접 지원
- 인덱스 활용 가능

**비교**:
```sql
-- IN 절 (문자열 생성 필요)
WHERE id IN (1, 2, 3, 4, 5)

-- ANY 연산자 (배열 파라미터)
WHERE id = ANY($1)  -- 더 효율적!
```

### 3. Rust HashMap을 이용한 O(1) 조회

#### 3.1 HashMap 생성

```rust
use std::collections::HashMap;

// user_id -> full_name 매핑
let user_name_map: HashMap<i32, Option<String>> = users
    .into_iter()
    .map(|user| (user.id, user.full_name))
    .collect();
```

#### 3.2 시간 복잡도 분석

**HashMap 생성**:
- 시간 복잡도: O(n) - n은 사용자 수
- 공간 복잡도: O(n)

**조회**:
- 시간 복잡도: O(1) - 평균적으로 상수 시간
- 해시 충돌이 없다면 매우 빠름

**전체 변환**:
- N개 annotation, M명의 고유 사용자
- HashMap 생성: O(M)
- 변환: O(N) × O(1) = O(N)
- **총 시간 복잡도: O(N + M)**

**대안 비교**:
```rust
// ❌ Vec::iter().find() 사용 시
// 각 annotation마다 O(M) 조회
// 총 시간 복잡도: O(N × M) - 매우 느림!

for annotation in annotations {
    let user = users.iter()
        .find(|u| u.id == annotation.user_id);  // O(M)
}

// ✅ HashMap 사용 시
// 각 annotation마다 O(1) 조회
// 총 시간 복잡도: O(N + M) - 빠름!

for annotation in annotations {
    let user_name = user_map.get(&annotation.user_id);  // O(1)
}
```

### 4. Rust 제네릭과 트레이트 바운드

#### 4.1 제네릭 타입 파라미터

**Before**:
```rust
pub struct AnnotationUseCase<A: AnnotationService> {
    annotation_service: A,
}
```

**After**:
```rust
pub struct AnnotationUseCase<A: AnnotationService, U: UserRepository> {
    annotation_service: A,
    user_repository: U,
}
```

**장점**:
- 컴파일 타임 타입 검증
- 제로 코스트 추상화
- 테스트 시 Mock 객체 주입 가능

#### 4.2 트레이트 바운드

```rust
impl<A: AnnotationService, U: UserRepository> AnnotationUseCase<A, U> {
    pub fn new(annotation_service: A, user_repository: U) -> Self {
        Self {
            annotation_service,
            user_repository,
        }
    }
}
```

**의미**:
- `A`는 `AnnotationService` 트레이트를 구현해야 함
- `U`는 `UserRepository` 트레이트를 구현해야 함
- 컴파일러가 타입 안전성 보장

### 5. Async/Await와 에러 처리

#### 5.1 비동기 헬퍼 메서드

```rust
async fn to_responses(
    &self,
    annotations: Vec<Annotation>,
) -> Result<Vec<AnnotationResponse>, ServiceError> {
    // 비동기 작업
    let users = self
        .user_repository
        .find_by_ids(&user_ids)
        .await  // await 포인트
        .map_err(|e| ServiceError::DatabaseError(e.to_string()))?;
    
    // 동기 작업 (메모리 내 처리)
    let user_map: HashMap<_, _> = users
        .into_iter()
        .map(|u| (u.id, u.full_name))
        .collect();
    
    Ok(responses)
}
```

**최적화 포인트**:
- 비동기 작업은 최소화 (DB 쿼리 1번만)
- 나머지는 동기 작업 (HashMap 생성, 변환)
- await 포인트가 적을수록 성능 향상

#### 5.2 에러 변환

```rust
.map_err(|e| ServiceError::DatabaseError(e.to_string()))?
```

**의미**:
- `sqlx::Error` → `ServiceError` 변환
- 레이어 간 에러 타입 분리
- 도메인 에러로 추상화

### 6. Option 타입 처리

#### 6.1 중첩된 Option 처리

```rust
// User가 Option<User>, full_name이 Option<String>
let user_name = self
    .user_repository
    .find_by_id(annotation.user_id)
    .await?
    .and_then(|user| user.full_name);
```

**동작**:
1. `find_by_id()` → `Result<Option<User>, Error>`
2. `.await?` → `Option<User>` (에러 전파)
3. `.and_then(|user| user.full_name)` → `Option<String>`
   - User가 Some이면 full_name 반환
   - User가 None이면 None 반환

#### 6.2 HashMap에서 Option 조회

```rust
let user_name = user_name_map
    .get(&annotation.user_id)  // Option<&Option<String>>
    .cloned()                   // Option<Option<String>>
    .flatten();                 // Option<String>
```

**단계별 설명**:
1. `get()`: HashMap에서 조회 → `Option<&Option<String>>`
2. `cloned()`: 참조를 값으로 복사 → `Option<Option<String>>`
3. `flatten()`: 중첩 Option 평탄화 → `Option<String>`

**flatten() 동작**:
```rust
Some(Some("홍길동")) → Some("홍길동")
Some(None)           → None
None                 → None
```

### 7. Arc와 Clone

#### 7.1 Arc (Atomic Reference Counting)

```rust
let user_repo = UserRepositoryImpl::new(pool.clone());

let annotation_use_case = Arc::new(AnnotationUseCase::new(
    annotation_service,
    user_repo.clone(),  // Arc::clone()
));
```

**Arc::clone() 특징**:
- 실제 데이터 복사 없음
- 참조 카운트만 증가 (원자적 연산)
- 매우 저렴한 연산 (포인터 복사 수준)
- 멀티스레드 안전

**메모리 구조**:
```
Arc<UserRepositoryImpl>
  ↓
[참조 카운트: 2] → [UserRepositoryImpl 데이터]
  ↑                        ↑
user_repo              annotation_use_case
```

### 8. 성능 최적화 기법

#### 8.1 Early Return

```rust
async fn to_responses(&self, annotations: Vec<Annotation>) -> Result<...> {
    if annotations.is_empty() {
        return Ok(Vec::new());  // 빈 목록은 즉시 반환
    }
    // ... 실제 처리
}
```

**효과**:
- 불필요한 DB 쿼리 방지
- 불필요한 HashMap 생성 방지

#### 8.2 HashSet으로 중복 제거

```rust
let user_ids: Vec<i32> = annotations
    .iter()
    .map(|a| a.user_id)
    .collect::<HashSet<_>>()  // 중복 제거
    .into_iter()
    .collect();
```

**시나리오**:
- 100개 annotation, 10명의 사용자
- HashSet 없이: 100개 ID 조회 (중복 포함)
- HashSet 사용: 10개 ID만 조회 (중복 제거)

**성능 향상**:
- DB 쿼리 크기 감소
- 네트워크 전송량 감소
- 메모리 사용량 감소

#### 8.3 Iterator 체이닝

```rust
let user_name_map: HashMap<i32, Option<String>> = users
    .into_iter()           // 소유권 이동 (복사 없음)
    .map(|user| (user.id, user.full_name))
    .collect();            // 한 번의 할당
```

**장점**:
- 중간 컬렉션 생성 없음
- 메모리 효율적
- 컴파일러 최적화 가능

## 🏗️ 아키텍처 패턴

### 1. Repository Pattern

**역할 분리**:
```
Domain Layer (인터페이스)
  ↓
trait UserRepository {
    async fn find_by_ids(&self, ids: &[i32]) -> Result<Vec<User>>;
}

Infrastructure Layer (구현)
  ↓
impl UserRepository for UserRepositoryImpl {
    async fn find_by_ids(&self, ids: &[i32]) -> Result<Vec<User>> {
        // PostgreSQL 구현
    }
}
```

**장점**:
- 도메인 로직과 데이터 접근 분리
- 테스트 용이성 (Mock 주입)
- 데이터베이스 교체 가능

### 2. Use Case Pattern

**책임**:
- 비즈니스 로직 조율
- 여러 서비스/리포지토리 조합
- DTO 변환

**구조**:
```rust
AnnotationUseCase
  ├─ annotation_service (도메인 로직)
  ├─ user_repository (데이터 접근)
  └─ to_response/to_responses (변환 로직)
```

### 3. DTO Pattern

**역할**:
- API 응답 형식 정의
- 도메인 엔티티와 분리
- 버전 관리 용이

**변환 흐름**:
```
Annotation (Entity)
  ↓ to_response()
AnnotationResponse (DTO)
  ↓ JSON 직렬화
API Response
```
