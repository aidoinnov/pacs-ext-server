# 기술 문서: 마스크 API 500 에러 수정

## 📚 개요

본 문서는 PACS 서버의 마스크 API에서 발생한 500 Internal Server Error의 원인과 해결 방법을 기술적으로 상세히 설명합니다.

## 🏗️ 아키텍처 배경

### Actix-web 프레임워크

Actix-web은 Rust 기반의 고성능 비동기 웹 프레임워크입니다.

#### Data Extractor 메커니즘

```rust
// 핸들러에서 Data<T> 사용
async fn create_mask(
    mask_use_case: web::Data<Arc<MaskUseCase<...>>>,  // ← Data extractor
    path: web::Path<(i32, i32)>,
    body: web::Json<CreateMaskRequest>,
) -> Result<HttpResponse, Error> {
    // ...
}
```

**동작 원리**:
1. `App::app_data(web::Data::new(value))`로 타입 등록
2. 핸들러 파라미터에서 `web::Data<T>` 사용
3. Actix-web이 런타임에 타입 매칭하여 주입 (Dependency Injection)

**중요**: 타입 시그니처가 **정확히 일치**해야 함!

## 🐛 문제 분석

### 에러 발생 시나리오

1. 클라이언트가 `POST /api/annotations/239/mask-groups/103/masks` 요청
2. Actix-web이 라우트 매칭 성공
3. 핸들러 `create_mask` 호출 시도
4. `web::Data<Arc<MaskUseCase<...>>>` 추출 시도
5. ❌ **app_data에 해당 타입이 등록되지 않음** → 500 에러

### 에러 메시지 분석

```
Failed to extract `Data<alloc::sync::Arc<pacs_server::application::use_cases::mask_use_case::MaskUseCase<...>>>`
```

이 메시지는 다음을 의미합니다:
- Actix-web이 `Arc<MaskUseCase<...>>` 타입을 찾으려 했으나
- `app_data`에 등록되지 않아 추출 실패
- 핸들러를 실행할 수 없어 500 에러 반환

### Rust 소유권 문제

```rust
// 문제 코드
let mask_service = Arc::new(MaskServiceImpl::new(...));

let mask_use_case = Arc::new(MaskUseCase::new(
    mask_service,  // ← mask_service의 소유권이 여기로 이동 (move)
    ...
));

// 이후 mask_service를 사용하려고 하면 컴파일 에러!
// error[E0382]: use of moved value: `mask_service`
```

**Rust의 소유권 규칙**:
- 각 값은 하나의 소유자(owner)만 가짐
- 소유권이 이동(move)되면 이전 소유자는 더 이상 사용 불가
- `clone()`을 사용하면 새로운 소유권 생성

**Arc의 특성**:
- `Arc::clone()`은 **참조 카운트만 증가** (얕은 복사)
- 실제 데이터는 복사되지 않음 (성능 영향 최소)
- 여러 곳에서 동일한 데이터를 공유 가능

## ✅ 해결 방법

### 1. Arc::clone() 사용

```rust
// ✅ 해결 코드
let mask_service = Arc::new(MaskServiceImpl::new(...));

let mask_use_case = Arc::new(MaskUseCase::new(
    mask_service.clone(),  // ← 참조 카운트만 증가, 소유권 유지
    mask_group_service.clone(),
    signed_url_service.clone(),
));

// mask_service를 계속 사용 가능!
```

**Arc::clone()의 동작**:
```
Before:
mask_service (Arc) → [MaskServiceImpl] (ref_count: 1)

After clone:
mask_service (Arc) ──┐
                     ├→ [MaskServiceImpl] (ref_count: 2)
mask_use_case (Arc) ─┘
```

### 2. app_data 등록

```rust
HttpServer::new(move || {
    App::new()
        // MaskUseCase 등록
        .app_data(web::Data::new(mask_use_case.clone()))
        // MaskGroupUseCase 등록
        .app_data(web::Data::new(mask_group_use_case.clone()))
        // SignedUrlService 등록
        .app_data(web::Data::new(signed_url_service.clone()))
        // 라우트 설정
        .service(
            web::scope("/api/annotations")
                .route("/{annotation_id}/mask-groups/{group_id}/masks", 
                       web::post().to(create_mask))
        )
})
```

**타입 매칭 과정**:
```
핸들러 시그니처:
  web::Data<Arc<MaskUseCase<MaskServiceImpl<...>, ...>>>

app_data 등록:
  web::Data::new(mask_use_case.clone())
  where mask_use_case: Arc<MaskUseCase<MaskServiceImpl<...>, ...>>

✅ 타입 일치! → 추출 성공
```

## 🔧 구현 세부사항

### MaskUseCase 제네릭 구조

```rust
pub struct MaskUseCase<MS, MGS, SUS>
where
    MS: MaskService + Send + Sync,
    MGS: MaskGroupService + Send + Sync,
    SUS: SignedUrlService + Send + Sync,
{
    mask_service: Arc<MS>,
    mask_group_service: Arc<MGS>,
    signed_url_service: Arc<SUS>,
}
```

**실제 타입 인스턴스**:
```rust
MaskUseCase<
    MaskServiceImpl<
        MaskRepositoryImpl,
        MaskGroupRepositoryImpl,
        UserRepositoryImpl
    >,
    MaskGroupServiceImpl<
        MaskGroupRepositoryImpl,
        AnnotationRepositoryImpl,
        UserRepositoryImpl
    >,
    SignedUrlServiceImpl
>
```

### 의존성 그래프

```
MaskUseCase
├── MaskService (MaskServiceImpl)
│   ├── MaskRepository (MaskRepositoryImpl)
│   ├── MaskGroupRepository (MaskGroupRepositoryImpl)
│   └── UserRepository (UserRepositoryImpl)
├── MaskGroupService (MaskGroupServiceImpl)
```

## 📊 성능 고려사항

### Arc::clone()의 비용

```rust
// Arc::clone()은 원자적 참조 카운트 증가만 수행
impl<T> Clone for Arc<T> {
    fn clone(&self) -> Arc<T> {
        // 원자적 연산 (atomic operation)
        self.inner().strong.fetch_add(1, Ordering::Relaxed);
        Arc { ptr: self.ptr, ... }
    }
}
```

**성능 특성**:
- 시간 복잡도: O(1)
- 메모리 복사: 없음 (포인터만 복사)
- 스레드 안전: 원자적 연산으로 보장
- 오버헤드: 매우 낮음 (나노초 단위)

### app_data 조회 비용

Actix-web은 내부적으로 `TypeId` 기반 해시맵을 사용:

```rust
// 의사 코드
HashMap<TypeId, Box<dyn Any>>
```

**조회 성능**:
- 시간 복잡도: O(1) (해시맵)
- 타입 안전성: 컴파일 타임 보장
- 런타임 오버헤드: 최소

## 🔒 보안 고려사항

### 타입 안전성

Rust의 강력한 타입 시스템으로 인해:
- 잘못된 타입 주입 불가능 (컴파일 타임 체크)
- 런타임 타입 캐스팅 에러 없음
- 메모리 안전성 보장

### 스레드 안전성

```rust
// Send + Sync 트레이트 바운드
where
    MS: MaskService + Send + Sync,
```

- `Send`: 스레드 간 소유권 이동 가능
- `Sync`: 여러 스레드에서 동시 참조 가능
- Actix-web의 멀티스레드 환경에서 안전

## 🎓 교훈

1. **Actix-web Data Extractor는 정확한 타입 매칭이 필수**
   - 제네릭 타입의 모든 파라미터가 일치해야 함
   - `app_data` 등록 누락 시 500 에러 발생

2. **Rust 소유권 시스템 이해 필수**
   - Move semantics를 이해하고 적절히 clone 사용
   - Arc::clone()은 성능 오버헤드가 거의 없음

3. **디버그 로깅의 중요성**
   - 에러 메시지에 전체 타입 시그니처 포함
   - 문제 진단에 매우 유용

4. **의존성 주입 패턴의 장점**
   - 테스트 용이성
   - 느슨한 결합 (Loose Coupling)
   - 확장성
