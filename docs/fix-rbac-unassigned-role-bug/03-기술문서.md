## 🗄️ 데이터베이스 스키마

### `security_user_project` 테이블

```sql
CREATE TABLE security_user_project (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES security_user(id) ON DELETE CASCADE,
    project_id INTEGER NOT NULL REFERENCES security_project(id) ON DELETE CASCADE,
    role_id INTEGER REFERENCES security_role(id) ON DELETE SET NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (user_id, project_id)
);
```

**주요 특징**:
- `role_id`는 NULL 허용 → Unassigned 상태 표현
- `(user_id, project_id)` UNIQUE 제약조건 → 중복 방지
- `ON DELETE SET NULL` → 역할 삭제 시 Unassigned 상태로 전환
- `ON DELETE CASCADE` → 사용자/프로젝트 삭제 시 참여 정보도 삭제

### 상태 정의

| `role_id` 값 | 상태 | 의미 |
|-------------|------|------|
| `NULL` | Unassigned | 프로젝트에 참여중이지만 역할 없음 |
| `1` (예시) | Assigned | 특정 역할 할당됨 (예: Viewer) |
| 레코드 없음 | Non-member | 프로젝트에 참여하지 않음 |

## 🔌 API 명세

### 1. 역할 할당 API

**Endpoint**: `PUT /api/projects/{project_id}/users/{user_id}/role`

**Request Body**:
```json
{
  "role_id": 1
}
```

**Response**:
- `200 OK`: 역할 할당 성공
- `404 Not Found`: 사용자, 프로젝트, 또는 역할이 존재하지 않음
- `500 Internal Server Error`: 서버 에러

**동작**:
1. 사용자-프로젝트 참여 정보 확인
2. **이미 참여중**: `role_id` UPDATE
3. **참여중 아님**: 새로운 참여 레코드 INSERT

---

### 2. 멤버 추가 API

**Endpoint**: `POST /api/projects/{project_id}/members`

**Request Body**:
```json
{
  "user_id": 8,
  "role_id": 1  // Optional, 없으면 Viewer 역할 자동 할당
}
```

**Response**:
- `200 OK`: 멤버 추가 성공
- `404 Not Found`: 사용자 또는 프로젝트가 존재하지 않음
- `500 Internal Server Error`: 서버 에러

**동작**:
1. `role_id`가 없으면 기본 역할(Viewer) 조회
2. 사용자-프로젝트 참여 정보 확인
3. **이미 참여중**: `role_id` UPDATE
4. **참여중 아님**: 새로운 참여 레코드 INSERT

## 🧠 핵심 로직 설명

### UPDATE vs INSERT 전략

#### 기존 방식 (문제 있음)
```rust
// 항상 INSERT 시도 → 중복 시 에러
sqlx::query("INSERT INTO security_user_project ...")
    .execute(pool)
    .await?;
```

#### 개선된 방식 (현재)
```rust
// 1. 존재 여부 확인
let is_member: bool = sqlx::query_scalar(
    "SELECT EXISTS(SELECT 1 FROM security_user_project 
     WHERE user_id = $1 AND project_id = $2)"
)
.bind(user_id)
.bind(project_id)
.fetch_one(&mut *tx)
.await?;

// 2. 분기 처리
if is_member {
    // UPDATE: 기존 레코드의 role_id 변경
    sqlx::query(
        "UPDATE security_user_project SET role_id = $1 
         WHERE user_id = $2 AND project_id = $3"
    )
    .bind(role_id)
    .bind(user_id)
    .bind(project_id)
    .execute(&mut *tx)
    .await?;
} else {
    // INSERT: 새로운 참여 레코드 생성
    sqlx::query(
        "INSERT INTO security_user_project 
         (user_id, project_id, role_id, created_at) 
         VALUES ($1, $2, $3, NOW())"
    )
    .bind(user_id)
    .bind(project_id)
    .bind(role_id)
    .execute(&mut *tx)
    .await?;
}
```

**장점**:
- ✅ Unassigned 상태 사용자 처리 가능
- ✅ 중복 INSERT 에러 방지
- ✅ 명확한 의도 표현
- ✅ 로깅으로 디버깅 용이

---

### 대안: UPSERT (ON CONFLICT) 방식

PostgreSQL의 `ON CONFLICT` 구문을 사용할 수도 있습니다:

```sql
INSERT INTO security_user_project (user_id, project_id, role_id, created_at)
VALUES ($1, $2, $3, NOW())
ON CONFLICT (user_id, project_id) 
DO UPDATE SET role_id = EXCLUDED.role_id;
```

**현재 방식을 선택한 이유**:
1. **명확성**: UPDATE와 INSERT가 명시적으로 분리되어 의도가 명확
2. **로깅**: 각 경우에 대해 다른 로그 메시지 출력 가능
3. **유연성**: 향후 UPDATE와 INSERT에 다른 로직 추가 가능
4. **가독성**: 코드 리뷰 및 유지보수 용이

## 🔒 트랜잭션 관리

### 트랜잭션 범위

```rust
async fn assign_user_role_in_project(
    &self,
    user_id: i32,
    project_id: i32,
    role_id: i32,
) -> Result<(), ServiceError> {
    let pool = self.project_repository.pool();
    let mut tx = pool.begin().await?;  // 트랜잭션 시작

    // 1. 사용자 존재 확인 (SELECT)
    // 2. 프로젝트 존재 확인 (SELECT)
    // 3. 역할 존재 확인 (SELECT)
    // 4. 멤버십 확인 (SELECT)
    // 5. UPDATE 또는 INSERT

    tx.commit().await?;  // 트랜잭션 커밋
    Ok(())
}
```

### 트랜잭션의 필요성

1. **원자성 (Atomicity)**: 모든 작업이 성공하거나 모두 실패
2. **일관성 (Consistency)**: 데이터베이스가 항상 일관된 상태 유지
3. **격리성 (Isolation)**: 동시 실행되는 트랜잭션 간 간섭 방지
4. **지속성 (Durability)**: 커밋된 변경사항은 영구적으로 저장

### 에러 발생 시 동작

```rust
// 에러 발생 시 자동 롤백
let mut tx = pool.begin().await?;

// ... 여러 DB 작업 ...

if error_condition {
    // tx.commit() 호출 안 함 → 자동 롤백
    return Err(ServiceError::SomeError);
}

tx.commit().await?;  // 성공 시에만 커밋
```

## ⚡ 성능 고려사항

### 쿼리 최적화

#### 1. EXISTS 쿼리 사용
```sql
-- ✅ 좋음: EXISTS는 첫 번째 매칭 레코드를 찾으면 즉시 반환
SELECT EXISTS(SELECT 1 FROM security_user_project 
              WHERE user_id = $1 AND project_id = $2)

-- ❌ 나쁨: COUNT는 모든 레코드를 세야 함
SELECT COUNT(*) FROM security_user_project 
WHERE user_id = $1 AND project_id = $2
```

#### 2. 인덱스 활용
```sql
-- UNIQUE 제약조건이 자동으로 인덱스 생성
UNIQUE (user_id, project_id)

-- 따라서 아래 쿼리는 인덱스 스캔으로 빠르게 실행
WHERE user_id = $1 AND project_id = $2
```

### 동시성 처리

#### 경쟁 조건 (Race Condition)

**시나리오**: 두 요청이 동시에 같은 사용자-프로젝트에 대해 역할 할당

```
Request A: SELECT EXISTS(...) → false
Request B: SELECT EXISTS(...) → false
Request A: INSERT INTO ... → 성공
Request B: INSERT INTO ... → UNIQUE 제약조건 위반 에러!
```

**해결 방안**:
1. **UNIQUE 제약조건**: 데이터베이스 레벨에서 중복 방지
2. **트랜잭션 격리 수준**: PostgreSQL 기본값 `READ COMMITTED` 사용
3. **에러 처리**: UNIQUE 제약조건 위반 시 재시도 또는 UPDATE로 전환 가능

## 🔮 향후 개선 방향

1. **UPSERT 방식 검토**: 성능 테스트 후 `ON CONFLICT` 방식 고려
2. **캐싱**: 자주 조회되는 멤버십 정보 캐싱
3. **배치 처리**: 여러 사용자에게 동시에 역할 할당하는 API 추가
4. **이벤트 발행**: 역할 할당 시 이벤트 발행하여 다른 시스템에 알림
5. **감사 로그**: 별도 테이블에 역할 변경 이력 저장
